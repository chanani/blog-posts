스프링 부트를 쓰면 별다른 설정 없이도 데이터베이스에 잘 연결되기에 무심코 지나치기 쉽지만, 그 뒤에서 묵묵히 일하고 있는 것이 바로 HikariCP입니다. 트래픽이 몰리는 순간 커넥션 풀 설정 하나가 서비스의 응답
속도를 좌우하기에 한번 정리해보려 합니다.

## ⭐️ 커넥션 풀과 HikariCP란?

### 커넥션 풀 (Connection Pool)

데이터베이스 커넥션을 맺는 일은 생각보다 비쌉니다. TCP 핸드셰이크, 인증, 세션 초기화 같은 과정을 매 요청마다 반복한다면 정작 쿼리를 실행하기도 전에 시간을 다 써버립니다. 그래서 미리 일정 개수의 커넥션을
만들어두고, 애플리케이션이 필요할 때 빌려 쓰고 반납하는 방식을 사용합니다. 이 "빌려주고 돌려받는" 창고 역할을 하는 것이 커넥션 풀입니다.

### HikariCP (Hikari Connection Pool)

HikariCP는 자바 진영에서 사실상 표준으로 자리 잡은 JDBC 커넥션 풀 라이브러리입니다. 가볍고 빠른 것이 가장 큰 특징이며, Spring Boot 2.0부터는 기본 커넥션 풀로 채택되어 있습니다. 그래서
우리가 의식하지 못하는 사이에 이미 쓰고 있는 경우가 대부분입니다. 참고로 'Hikari(光, ひかり)'는 일본어로 '빛'을 의미하는데, 그만큼 빠르다는 자신감이 담긴 이름입니다.

## 🔎 왜 빠를까?

HikariCP가 "빠르다"고 말할 때는 단순한 마케팅이 아니라 내부 구현 차원의 최적화가 뒷받침됩니다. 대표적으로 세 가지가 자주 언급됩니다.

### ConcurrentBag

일반적인 큐 기반 자료구조 대신 ConcurrentBag이라는 자체 컬렉션을 사용합니다. 커넥션을 빌리고 반납할 때의 락 경합(lock contention)을 줄이고, 같은 스레드가 직전에 반납한 커넥션을 다시 빌려
쓰도록 유도해 캐시 효율을 높이는 구조입니다.

### FastList

커넥션에서 열린 Statement들을 추적할 때 사용하는 리스트입니다. 자바 기본 ArrayList의 범위 체크 같은 오버헤드를 덜어내고, 닫을 때 보통 마지막에 추가된 것부터 닫힌다는 점을 이용해 역순 탐색에
최적화되어 있습니다.

### 바이트코드 최적화

라이브러리 자체의 바이트코드 크기를 줄이고 메서드를 간결하게 유지해, JIT 컴파일러가 인라이닝하기 좋은 형태로 다듬어 두었습니다. 작은 코드가 빠른 코드라는 철학이 곳곳에 녹아 있습니다.

물론 이 내부 동작을 외우고 있을 필요는 없습니다. 다만 "그냥 빠르다"가 아니라 "왜 빠른지" 한 번쯤 들여다보면, 설정값을 만질 때의 감각이 달라집니다.

## 🔄 커넥션은 어떻게 관리될까?

설정값을 제대로 이해하려면, 풀 안에서 커넥션 하나가 태어나서 사라지기까지의 흐름을 먼저 그려보는 것이 좋습니다.

### 1. 빌리기 (borrow)

대부분 '커넥션을 획득한다'라고 표현합니다. 애플리케이션이 `dataSource.getConnection()`을 호출하면, HikariCP는 풀(ConcurrentBag)에서 사용 가능한 커넥션을 하나 찾아
건네줍니다. 이때 같은 스레드가 직전에 반납한
커넥션을 우선적으로 다시 빌려주려 시도합니다. 만약 빌려줄 커넥션이 하나도 없다면, 새로 만들거나(최대치 미만일 때) connectionTimeout만큼 기다립니다. 그 안에도 확보하지 못하면 예외가
발생합니다.

### 2. 사실은 "프록시"를 빌려준다

여기서 핵심적인 사실 하나. 우리가 받는 Connection은 실제 DB 커넥션이 아니라 그것을 감싼 프록시 객체(ProxyConnection)입니다. 이 한 겹의 포장 덕분에 다음 동작이 가능해집니다.

### 3. 반납 (return) — `close()`의 비밀

```java
try (Connection conn = dataSource.getConnection()) {
    // 쿼리 실행
} // 여기서 conn.close()가 호출됨
```

가장 헷갈리기 쉬운 부분입니다. 위 코드에서 `close()`가 호출되지만, 실제 DB 커넥션은 닫히지 **않습니다**. 프록시의 `close()`는 "이 커넥션을 풀에 돌려놓는다"는 의미로 동작합니다. 즉, 우리가
평소에 쓰는 close는 '종료'가 아니라 '반납'인 셈입니다. 커넥션 풀의 재사용은 바로 이 지점에서 일어납니다.

### 4. 검증 (validation)

커넥션을 빌려주기 직전, HikariCP는 그 커넥션이 아직 살아 있는지 확인합니다. 기본적으로 JDBC4의 `isValid()`를 사용합니다. 다만 방금 전까지 잘 쓰이던 커넥션까지 매번 검사하면
비효율적이므로, 마지막 사용 시점으로부터 아주 짧은 시간(기본 500ms) 안이라면 검증을 건너뛰어 성능을 챙깁니다.

### 5. 정리와 폐기 (housekeeping)

HikariCP는 백그라운드에서 주기적으로 도는 하우스키퍼(HouseKeeper) 스레드를 두고 풀을 관리합니다. 이 스레드가 하는 일은 크게 두 가지입니다.

- **유휴 커넥션 정리**: idleTimeout을 넘기도록 쓰이지 않은 커넥션을, minimumIdle 아래로 내려가지 않는 선에서 닫습니다.
- **수명 다한 커넥션 교체**: maxLifetime에 도달한 커넥션을 폐기하고 새것으로 갈아끼웁니다. 이때 모든 커넥션이 동시에 만료되어 한꺼번에 끊기는 상황을 막기 위해, 만료 시점을 살짝씩 흩뜨려(
  jitter) 둡니다.

정리하면, 풀은 단순히 커넥션을 쌓아두는 통이 아니라 '빌려주고 → 검증하고 → 반납받고 → 늙은 것을 갈아끼우는' 순환을 끊임없이 돌리는 살아 있는 시스템에 가깝습니다. 아래 설정값들은 결국 이 순환의 속도와
타이밍을 조절하는 손잡이인 셈입니다.

## 🛠️ 핵심 설정값 다루기

HikariCP에서 자주 만지게 되는 설정들입니다. 기본값과 함께 정리해두면 좋습니다.

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 10      # 풀이 가질 수 있는 최대 커넥션 수 (기본 10)
      minimum-idle: 10           # 유휴 상태로 유지할 최소 커넥션 수 (기본: max와 동일)
      connection-timeout: 30000  # 커넥션을 기다리는 최대 시간 (기본 30초)
      idle-timeout: 600000       # 유휴 커넥션이 정리되기까지의 시간 (기본 10분)
      max-lifetime: 1800000      # 커넥션의 최대 수명 (기본 30분)
```

maximumPoolSize — 가장 중요하고, 가장 많이 오해받는 값
"커넥션이 많을수록 빠르겠지"라는 직관은 틀린 경우가 많습니다. 커넥션이 늘어나면 그만큼 DB가 처리해야 할 동시 작업이 많아지고, 컨텍스트 스위칭과 락 경합이 심해져 오히려 느려질 수 있습니다. HikariCP
문서에서 제안하는 사이징 공식은 다음과 같습니다.

```
connections = (코어 수 * 2) + 디스크 스핀들 수
```

즉, 수백 개의 커넥션이 아니라 의외로 작은 숫자가 정답인 경우가 많습니다. 풀 사이즈는 늘리기 전에 줄여보는 실험부터 해보는 편이 좋습니다.

### maxLifetime — DB 타임아웃보다 짧게

이 값은 커넥션이 풀 안에서 살아 있을 수 있는 최대 시간입니다. 주의할 점은, 데이터베이스나 그 앞단의 인프라(예: 방화벽, L4)가 끊어버리는 시간보다 반드시 몇 초 짧게 설정해야 한다는 것입니다. 그렇지 않으면
이미 죽은 커넥션을 풀이 살아 있다고 착각하고 빌려주면서 간헐적인 connection 관련 예외가 발생합니다. 원인을 찾기 가장 어려운 종류의 버그입니다.

### minimumIdle — 굳이 건드리지 않기

HikariCP 제작자는 minimumIdle을 maximumPoolSize와 동일하게 두는 것(기본 동작)을 권장합니다. 풀을 고정 크기로 운영하는 편이 트래픽이 튈 때 커넥션을 새로 만드느라 지연되는 상황을
막아주기 때문입니다.

## ⚠️ 흔히 마주치는 함정

### 커넥션 누수 (Connection Leak)

빌려온 커넥션을 반납하지 않으면, 풀은 점점 빌려줄 커넥션이 없어집니다. 결국 connectionTimeout만큼 기다리다 예외가 터집니다. 보통은 트랜잭션을 프레임워크(@Transactional 등)에 맡기면
자동으로 처리되지만, 직접 커넥션을 다룰 때는 try-with-resources로 확실히 닫아주어야 합니다. leakDetectionThreshold를 설정하면 오래 반납되지 않은 커넥션을 로그로 경고해주니 디버깅에
유용합니다.

### 풀 사이즈 = 만능 해결책이라는 착각

응답이 느릴 때 풀 사이즈부터 키우고 싶어지지만, 앞서 말했듯 이는 종종 문제를 악화시킵니다. 느린 쿼리, 부족한 인덱스, 길게 잡힌 트랜잭션이 진짜 원인인 경우가 훨씬 많습니다. 풀은 증상을 가릴 뿐 병을 고치지
못합니다.
